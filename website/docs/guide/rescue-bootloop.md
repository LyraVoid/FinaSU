刷机时可能遇到设备“变砖”的情况。如果只是刷入了不合适的启动分区镜像或安装了有问题的模块，通常仍然可以通过正确操作恢复。本文按照故障来源提供急救流程，但不要为了尝试而随手刷入未知镜像。

## 刷入分区镜像时变砖

刷入由 FinaSU 修补后的启动分区镜像后无法开机，常见原因包括：

- 设备不在该 LKM 的 KMI 支持范围内。
- 使用了错误或不匹配的启动分区镜像。
- 修补了错误的 `boot`、`init_boot` 或 A/B 槽位。
- 同时使用了多个内核级 Root 实现。
- 使用了来源不明或不兼容的 AnyKernel3 安装包。

::: warning

这类故障发生在内核或启动镜像层面，下面的音量键安全模式可能没有机会运行。应先恢复匹配的原厂启动分区，而不是反复重启同一个镜像。

:::

## 刷入模块变砖

这是更常见的情况。模块可能不支持当前设备，也可能通过 `post-fs-data.sh`、`service.sh`、元模块脚本或受管内核模块破坏了启动环境。

::: important

模块以高权限运行。来源不明或经过他人二次分发的模块可能包含恶意代码，并导致设备无法启动甚至发生不可逆损坏。只安装来源明确、支持当前系统和设备的模块。

:::

如果设备安装或更新模块后开始启动循环，优先尝试 FinaSU 安全模式。如果安全模式也无法进入，再恢复原厂启动分区。

## 救砖机制

FinaSU 内置了一套启动早期安全模式：检测到触发条件后，会禁用普通模块和受管内核模块，并跳过模块脚本、Folk Mount、FolkZygisk 和 Sui 等启动流程。

### 音量键救砖

在设备开始启动、屏幕刚亮起时，尽快执行 3 次“按下音量减键后松开”。FinaSU 会在启动早期统计按键次数，达到 3 次后启用安全模式。

::: info

音量键救砖必须尽早操作。FinaSU 只采集启动早期的按键，在进入 `post-fs-data` 后会停止监听。错误的 LKM、KMI 不匹配或损坏的启动镜像可能导致驱动根本没有运行，此时音量键无法触发安全模式。

:::

安全模式会为全部普通模块和受管内核模块写入禁用标记。这些标记在重启后继续保留；安全模式本身只对当前启动会话生效。普通重启并恢复正常启动后，不要一次启用全部模块，而应逐个启用并重启，找出真正导致问题的模块。

::: tip

如果延迟加载（越狱）模式没有采集到启动阶段的音量键，不能依靠这套音量键流程进入安全模式。

:::

### REC 启动安全模式

一些 ROM 可以在 Recovery 中开启 Android 自带的安全模式。FinaSU 会识别 `persist.sys.safemode` 或 `ro.sys.safemode`，因此进入 Android 安全模式时也会跳过模块启动流程。

::: important

成功启动后第三方应用全部消失？

这通常表示设备进入了 Android 安全模式，而不只是 FinaSU 安全模式。管理器本身也是第三方应用，因此可能暂时不可见。再次普通重启通常可以退出 Android 安全模式；FinaSU 写入的模块禁用标记仍会保留，管理器恢复后再处理问题模块。

:::

安全模式不能撤销已经进入内核的异常代码，也不能恢复内核 panic。如果安全模式后仍然无法进入系统，应恢复原厂启动分区。

## 恢复原厂分区镜像

安全模式无法进入时，应刷回安装时实际修改的启动分区。镜像必须同时匹配设备型号、地区版本、Android 构建、安全补丁级别和槽位。

优先使用安装前保存的原厂镜像。没有备份时，从设备厂商提供的完整固件包中提取。不要使用其他机型、其他系统版本或第三方网站重新打包的“通用救砖镜像”。

### 第三方 Recovery

如果设备可以进入第三方 Recovery，可以在其中把原厂 `boot` 或 `init_boot` 镜像刷入对应分区。操作前确认 Recovery 显示的分区名和目标槽位，不要顺便格式化 `/data` 或其他分区。

如果设备有厂商 Recovery，并且官方支持完整 OTA 包或本地升级，也可以按照厂商说明恢复整包。此流程可能覆盖系统或清除数据，执行前先确认后果。

### Fastboot

如果设备可以进入 Fastboot，先连接电脑并确认设备可见：

```sh
fastboot devices
```

没有输出时不要继续刷写。先检查数据线、USB 接口、平台驱动和 Fastboot 驱动。

A/B 设备先确认当前槽位：

```sh
fastboot getvar current-slot
```

只刷入 FinaSU 实际修改过的分区：

::: code-tabs

@tab:active boot

```sh
fastboot flash boot boot.img
```

@tab init_boot

```sh
fastboot flash init_boot init_boot.img
```

:::

如果 Fastboot 不会自动选择当前槽位，应在分区名后加上 `_a` 或 `_b`，例如 `boot_b`、`init_boot_b`。不要凭猜测刷入另一个槽位。

刷写完成后重启：

```sh
fastboot reboot
```

::: danger

`boot` 和 `init_boot` 不能混用。必须根据管理器当时的修补结果或安装日志，确认实际修改的是哪个分区。错误分区、错误系统版本和错误槽位都可能让设备继续无法启动。

:::

如果故障发生在 OTA 后“安装到未使用的槽位”，并且另一个槽位仍是此前可启动的系统，可以尝试切回该槽位：

```sh
fastboot getvar current-slot
fastboot set_active a
fastboot reboot
```

上面的 `a` 只是示例，必须替换成另一个槽位。旧槽位已经被改写、OTA 已经合并，或无法确认两个槽位的系统版本时，不要使用这种方法。

::: danger

如果设备无法进入系统、Fastboot 和 Recovery，不要继续尝试不明来源的 EDL、Firehose 或其他深层刷机工具。此类工具具有严格的机型和认证差异，错误文件可能造成不可逆损坏。请先尝试官方说明书中的强制重启，再联系厂商售后或使用该机型官方支持的恢复流程。

:::

设备恢复后，不要立刻重新安装模块或 Root。先确认设备型号、Android 构建、KMI 和当前槽位，再检查是 LKM、启动分区、槽位、AnyKernel3、模块脚本还是多 Root 冲突导致了问题。保留安装方式和启动日志，必要时参考[日志与反馈](/troubleshoot/logs/)寻求帮助。
