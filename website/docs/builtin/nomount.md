# NoMount

<Badge text="VFS 后端" type="info" /> <Badge text="最低 API 22" type="warning" /> <Badge text="默认可见性相反" type="danger" />

==NoMount 通过内核侧 VFS 查找与目录遍历重定向注入模块文件==，不建立传统挂载。因此进程的挂载表可以保持原样，但文件系统视图仍由内核按规则改写。

::: important 不显示挂载不等于“完全无痕”

NoMount 隐藏的是一类传统挂载痕迹。文件内容、打开的文件描述符、SELinux、审计日志、系统属性或其他行为差异仍可能被检测。它不保证通过所有完整性检查。

:::

## 在 Folk Mount 中启用

NoMount 不是单独切换的开关。打开 **设置 → 功能 → Folk Mount**，把模式改为 **Built-in (VFS)**，然后重启。

:::: steps

1. **先配置例外应用**

   NoMount 的默认可见性与内置 Magic Mount 相反。切换前在 NoMount 页面选择哪些应用应看到原厂文件系统。

2. **选择 Built-in (VFS)**

   管理器会提示可见性变化。确认后写入下次启动配置。

3. **重启设备**

   驱动加载和规则注入发生在启动阶段。当前启动的 Folk Mount 提供者不会热切换。

4. **检查驱动与规则**

   确认驱动为 **就绪**，并检查“已生效 / 预期”规则数。规则为 0 不代表驱动坏了，可能只是没有模块贡献可注入文件。

5. **用例外应用验证**

   普通应用应看到注入文件，例外应用应看到原厂视图。共享 UID 的应用会一起受影响。

::::

## 驱动

NoMount 可以来自内核内建支持，也可以来自与当前 KMI 匹配的 `.ko`。两种来源在内核 API 就绪后使用同一套规则协议。

::: table 驱动状态

| 状态 | 含义 | 常见处理 |
| --- | --- | --- |
| **就绪 / Ready** | 驱动 API 可响应，版本满足最低要求 | 继续检查规则和提供者 |
| **不可用 / Absent** | 没有内建支持，也没有已加载模块 | 重启、执行一次注入，或检查安装包是否带当前 KMI 资产 |
| **版本不匹配 / Outdated** | 驱动存在，但 API 低于 22 | 升级内核侧实现；内建旧驱动不能由用户态直接替换 |

:::

页面还会区分：

- **内核内建**：驱动随内核镜像提供，无需额外加载。
- **内核模块**：驱动以当前 KMI 的 `.ko` 形式加载。
- **由其它模块接管**：另一个已安装模块驱动同一个 NoMount 内核接口，内置后端让位。

::: warning 加载成功不等于驱动可用

内核模块加载器会处理 vermagic 和符号重定位，但“加载调用返回”仍可能得到一个不能响应的驱动。因此 NoMount 会在加载后再次探测 API，只有可响应且版本合格才算就绪。

:::

## 驱动失败与启动保护

NoMount 会先准备驱动，再发布规则。以下情况会让本次启动回退到内置 Magic Mount：

- 当前安装包没有匹配 KMI 的模块，且内核没有提供驱动。
- 驱动加载失败，或加载后 API 版本仍不合格。
- 上一次加载或注入阶段没有完成，启动流程保守地不重复同一路径。
- 规则发布失败。

回退会写入 warning，说明本次实际是由内置引擎完成挂载。==配置模式仍然是 Built-in (VFS)==，不要因为看到回退就反复切换模式。

::: danger “再次选择 NoMount”也是重试动作

如果上一次驱动加载留下未完成保护记录，重新选择 NoMount 会清除该记录，允许下一次启动重试。已经多次卡在 NoMount 阶段时，先保留日志并准备救砖手段，不要无限次重试。

:::

## 注入规则

NoMount 从已启用模块的 `system/` 树生成重定向规则，包括普通文件重定向、目录替换和 whiteout。常见统计有三类：

- **预期规则**：当前模块计划应发布的规则数。
- **已生效规则**：内核当前持有、由模块贡献的非虚拟目录规则。
- **内核总规则**：包含驱动为实现深层路径自动创建的虚拟目录。

:::: field-group

::: field 普通重定向
@type `文件或目录`
虚拟路径由另一个真实路径提供内容，但进程看到的仍是指定虚拟路径。
:::

::: field 目录替换
@type `Opaque`
该目录直接使用模块树，不再把原厂目录内容与模块内容继续合并。
:::

::: field Whiteout
@type `隐藏`
让某个路径表现为不存在，而不是把它重定向到另一个文件。
:::

::: field 跳过模块
@type `诊断`
模块目录不可读、路径不合法、符号链接越界或规则无法安全生成时，模块可能被跳过并记录原因。
:::

::::

## 热注入与撤下

NoMount 支持在当前启动内操作单个模块：

- 点击模块执行 **热注入**，把该模块当前规则加入内核。
- 对单个模块执行 **撤下**，移除它的规则，直到下次重启重新生成。
- **清空规则**会移除全部重定向，但保留例外应用；重启后恢复。
- **清空全部**会同时清空规则和例外应用；重启后恢复启动计划。

热操作适合定位单个模块。它不会重新安装模块，也不会改变模块是否启用。

## 可见性模型

这是切换到 NoMount 时最容易踩坑的部分。

::: table 两种后端的默认视图

| 后端 | 默认行为 | 例外列表的作用 |
| --- | --- | --- |
| **内置 Magic Mount** | 按 App Profile 的“卸载模块”策略向非 Root 应用隐藏 | 由 App Profile 决定 |
| **NoMount** | 所有应用默认都能看到注入文件 | 例外 UID 看到原厂文件系统 |

:::

NoMount 的例外应用不是“允许 Root 的应用”，也不是“允许联网的应用”。它只表示这些 UID 不应用模块重定向。

### 隔离进程

开启 **对隔离进程隐藏** 后，WebView、SDK 沙箱等隔离进程也看到原厂文件系统。这个选项和普通例外 UID 是两套控制，不要把它们当成同一种列表。

### 跟随应用 Profile

“跟随应用 Profile”只会执行一次复制：把列表范围内、Profile 中启用了“卸载模块”的应用加入 NoMount 例外。之后 App Profile 再变化，不会自动同步。

::: warning 第一次复制可能选中很多应用

默认非 Root Profile 对多数应用启用“卸载模块”。在 NoMount 页面点击“跟随应用 Profile”时，可能一次选中大量应用。先查看选中数量，再保存。

:::

### 共享 UID

Android 应用可以共享 UID。NoMount 按 UID 而不是只按包名匹配，所以给一个应用设置例外时，同 UID 的其他应用也会看到原厂视图。

## 状态与诊断

:::: collapse accordion

### 驱动就绪，但规则数是 0

这可能正常。检查是否有模块包含可注入的 `system/` 路径、模块是否被禁用或标记 `skip_mount`，以及规则是否被“清空规则”操作移除。

### 显示“由其它模块接管”

已安装的某个模块正在驱动同一个 NoMount 内核接口。内置后端会主动退出，避免两套程序同时写规则。到该模块的管理入口检查，不要强行让两套同时注入。

### 例外应用仍然看到模块文件

确认改动已经保存到内核，而不只是编辑了列表；确认应用 UID 没有因重装或工作资料变化；共享 UID 的其他应用可能重新暴露同一视图。必要时彻底重启目标应用。

### 切回内置 Magic Mount 后模块又出现了

说明 NoMount 的例外列表已经生效，而内置引擎按 App Profile 的策略显示。切回前先重新核对 Profile 的“卸载模块”设置。

### 没有挂载记录，为什么检测还能发现差异

NoMount 只改变 VFS 视图，不负责隐藏文件内容、进程映射、系统属性或 SELinux 审计。完整性检测并不只检查 `/proc/mounts`。

::::

## 命令与数据位置

```file-tree title="NoMount 相关位置"
/data/adb/ksu
├── mount_mode                  # 选择 nomount 后才会启用 VFS 后端
├── nomount_runtime             # 最近一次驱动与规则注入结果
├── nomount_uids                # 例外 UID 与隔离进程选项
├── nomount_last_action         # 最近一次热操作
├── mount_log                   # 规则和跳过原因
└── workdir/                    # 规则准备与启动工作目录
```

::: code-tabs

@tab 管理器

```text
设置 → 功能 → Folk Mount → NoMount
查看驱动、规则、模块贡献、例外应用和最近操作
```

@tab 状态

```sh
/data/adb/ksud nomount status --json
```

@tab 预演

```sh
/data/adb/ksud nomount inject --dry-run --verbose
```

:::

预演只生成和报告规则，不接触内核。它适合确认某个模块为什么被跳过。

不要直接编辑 `nomount_uids` 或手工调用驱动协议。规则和 UID 列表需要与内核当前状态同步，管理器与 `ksud` 会处理存储、校验和错误回报。

## 推荐用法

1. **先决定可见性，再切后端。** 不要等重启后才发现所有应用都看到模块文件。
2. **先用例外列表做最小范围验证。** 不要一次把整套应用策略迁移到 NoMount。
3. **规则异常时先预演。** 检查模块贡献和跳过原因，再决定热注入或回退。
4. **不要用 NoMount 承诺“完全隐身”。** 它解决的是一类挂载痕迹，不是全栈反检测。
